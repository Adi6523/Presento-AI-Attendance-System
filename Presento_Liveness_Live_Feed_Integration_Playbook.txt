PRESENTO ATTENDANCE SYSTEM
LIVE CAMERA + LIVENESS FEED INTEGRATION PLAYBOOK

PURPOSE
=======
This document specifies how to connect the already-tested live Logitech C270
camera feed from the Raspberry Pi 4 to the Presento liveness pipeline running
on the Windows laptop.

This is the next integration layer after the successful:

    C270 -> Raspberry Pi -> live network stream -> Windows/OpenCV

test.

The objective is:

    C270
      ->
    Raspberry Pi 4
      ->
    live network stream
      ->
    Windows laptop
      ->
    OpenCV frame
      ->
    Presento liveness.py
      ->
    liveness result
      ->
    Presento recognition / attendance pipeline

No MP4 files are used.
No 20-second recording is used.
No SCP is used.
No human prompt is required during normal operation.

IMPORTANT ARCHITECTURE RULE
===========================
The camera transport that has already been tested successfully must remain the
camera transport.

Do NOT replace the working live stream with:

    C270 -> MP4 -> laptop -> liveness

The production/test path is:

    C270 -> V4L2 -> OpenCV -> network -> laptop -> liveness

The liveness detector operates on live OpenCV frames.

The system should prioritize current frames over stale frames. Do not create an
unbounded queue of camera frames.

WHY MJPG
========
The C270 supports YUYV and MJPEG.

1280x720 YUYV was previously observed at approximately 10 FPS when 30 FPS
was requested.

MJPG achieved approximately 29.78 FPS in the tested OpenCV configuration after:

    exposure_dynamic_framerate=0

Therefore MJPG remains the preferred transport format.

LIVE STREAM PROTOCOL
====================
The current test protocol is:

    4-byte unsigned big-endian JPEG length
    JPEG payload
    4-byte unsigned big-endian JPEG length
    JPEG payload
    ...

Example:

    [00 00 12 34][JPEG bytes]
    [00 00 11 98][JPEG bytes]
    ...

This makes every JPEG frame independently decodable.

The Pi does not save frames to disk.

The laptop decodes the received JPEG immediately with:

    cv2.imdecode()

NO FRAME BACKLOG
================
The liveness pipeline must not process an old queue of frames.

Bad architecture:

    camera
       |
       v
    frame queue
       |
       +-> frame 1
       +-> frame 2
       +-> frame 3
       +-> frame 4
       +-> ...
       |
       v
    liveness

If liveness takes longer than the camera FPS, this creates increasing latency.

Preferred architecture:

    camera
       |
       v
    latest live frame
       |
       v
    liveness
       |
       v
    result

When a newer frame arrives, an older unprocessed frame can be replaced.

This keeps liveness close to real time.

MINIMAL TEST RECEIVER
=====================
The following is a transport-level reference receiver.

Save as:

    %USERPROFILE%\presento_liveness_receiver.py

Code:

    import cv2
    import socket
    import struct
    import numpy as np
    import time

    PI_IP = "10.241.151.190"
    PORT = 5001

    def recv_exact(sock, size):
        data = bytearray()

        while len(data) < size:
            chunk = sock.recv(size - len(data))

            if not chunk:
                return None

            data.extend(chunk)

        return bytes(data)

    def main():
        sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

        print(f"Connecting to Raspberry Pi {PI_IP}:{PORT}...")
        sock.connect((PI_IP, PORT))
        print("Connected to Raspberry Pi.")

        frame_count = 0
        start = time.time()

        while True:
            header = recv_exact(sock, 4)

            if header is None:
                print("Pi disconnected.")
                break

            size = struct.unpack("!I", header)[0]

            if size <= 0 or size > 5_000_000:
                print("Invalid frame size:", size)
                break

            jpeg = recv_exact(sock, size)

            if jpeg is None:
                print("Frame reception stopped.")
                break

            frame = cv2.imdecode(
                np.frombuffer(jpeg, dtype=np.uint8),
                cv2.IMREAD_COLOR
            )

            if frame is None:
                continue

            frame_count += 1

            elapsed = time.time() - start

            if elapsed >= 1.0:
                fps = frame_count / elapsed

                cv2.putText(
                    frame,
                    f"Live FPS: {fps:.1f}",
                    (20, 40),
                    cv2.FONT_HERSHEY_SIMPLEX,
                    1,
                    (0, 255, 0),
                    2
                )

            cv2.imshow("Presento - Live Liveness Feed", frame)

            if cv2.waitKey(1) & 0xFF == ord("q"):
                break

        sock.close()
        cv2.destroyAllWindows()

    if __name__ == "__main__":
        main()

This receiver is a transport/display test.

It is NOT a replacement for the existing Presento liveness algorithm.

WARM-UP
=======
The C270 can produce several invalid/dark frames immediately after opening.

Observed historical behavior:
- some tests became clear around the third frame
- another 1280x720 MJPG test had frames 1-22 at mean brightness 2.00
- frame 23 became valid

Therefore:

    DO NOT:
        sleep(1)
        capture exactly one frame
        assume it is valid

Instead:

    open camera
       |
       v
    read frames continuously
       |
       v
    validate
       |
       v
    first valid frame
       |
       v
    liveness pipeline

No frame queue is required.

FRAME VALIDATION
================
Basic transport validation:

    frame is not None
    frame.size > 0
    width >= 320
    height >= 240

Known startup-invalid condition:

    mean approximately 2
    min approximately 2
    max approximately 2

A basic rejection rule can be:

    mean <= 2.5
    AND
    min >= 1
    AND
    max <= 3

This is specifically based on the tested C270 startup behavior.

Do not use this brightness rule as the liveness detector.

A dark real face and a bright spoof are different concepts.

QUALITY VS LIVENESS
===================
Keep these separate:

QUALITY:
- Is the face usable?
- Is it sufficiently sharp?
- Is exposure acceptable?
- Is the face large enough?
- Is the crop suitable?

LIVENESS:
- Does the existing liveness model/pipeline classify the presented face as
  live rather than a spoof?

RECOGNITION:
- Whose face is it?

Attendance should require the appropriate combination.

RECOMMENDED PRODUCTION RECEIVER DESIGN
======================================
Use three logical components:

    CameraTransport
        |
        v
    LatestFrameStore
        |
        v
    LivenessProcessor

CameraTransport:
- receives network JPEGs
- decodes them
- replaces latest frame
- never builds an unbounded queue

LatestFrameStore:
- contains at most one current frame
- thread-safe

LivenessProcessor:
- retrieves newest available frame
- runs detection
- runs quality
- runs liveness
- forwards only valid liveness results

This separation prevents the network code from being coupled to the AI model.

THREADING MODEL
===============
Recommended:

    Network receiver thread
             |
             v
       latest_frame
             |
             v
       AI/liveness thread

The network receiver should not wait for the liveness model to finish.

If the model is busy:
- incoming frames replace the latest frame
- stale frames are not processed later

This maintains low latency.

IMPORTANT:
If the existing Presento code is not thread-safe, do not run the same liveness
model instance concurrently from multiple threads. Use one liveness worker or
a documented thread-safe model architecture.

LIVENESS MODEL INITIALIZATION
=============================
Model loading should happen once at application startup.

Bad:

    every frame:
        load model
        run liveness

Good:

    application start:
        load liveness model

    every frame:
        run existing liveness function

This prevents severe latency.

FACE DETECTOR INITIALIZATION
============================
Similarly, initialize the face detector once.

Do not load detector/model weights on every frame.

Recommended lifecycle:

    startup
      ->
    load face detector
      ->
    load quality model/config
      ->
    load liveness model
      ->
    connect camera
      ->
    process live frames

LIVENESS PERFORMANCE
====================
Measure separately:

    received_fps
    decoded_fps
    face_detection_fps
    liveness_fps
    recognition_fps

Do not report the camera's configured 30 FPS as the liveness processing FPS.

Example:

    camera:      29.8 FPS
    receiver:    29.5 FPS
    liveness:    12 FPS

This is possible and does not mean the camera is running at 12 FPS.

In that case, latest-frame processing prevents liveness latency from growing.

ATTENDANCE DE-DUPLICATION
=========================
A person may remain in front of the camera for hundreds of frames.

Do not create hundreds of attendance records.

Conceptual policy:

    liveness PASS
       +
    recognition MATCH
       +
    attendance not already recorded
       ->
    create attendance event

Use the existing Presento database/API rules.

Do not invent a new MySQL schema if the project already has one.

FASTAPI INTEGRATION
===================
Once liveness and recognition are valid:

    liveness
       ->
    recognition
       ->
    attendance service
       ->
    FastAPI
       ->
    MySQL
       ->
    React dashboard

The liveness module itself should ideally not directly perform database writes.

Recommended separation:

    vision layer
        returns result

    attendance layer
        decides whether to record

    API layer
        persists / exposes event

    database layer
        stores data

This makes testing easier.
