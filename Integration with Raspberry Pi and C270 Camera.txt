PRIMARY REQUIREMENT
===================
The Raspberry Pi is the camera edge device.

The laptop is the AI/processing device.

The Pi must continuously capture the C270 and send the live camera frames directly
to the laptop. The integration must not intentionally build a frame queue, file
buffer, recording buffer, or batch-processing buffer.

The laptop-side receiver must always process the newest frame available. If the
AI processing temporarily becomes slower than the camera, stale frames must not
accumulate. A bounded latest-frame mechanism is preferable to an unbounded queue.

IMPORTANT ENGINEERING LIMITATION
=================================
"Live with no buffers" means NO INTENTIONAL APPLICATION-LEVEL FRAME BUFFERING.
Operating-system socket buffers and the camera/USB driver's internal buffers cannot
be eliminated completely.

If the requirement is literally "every physical camera frame must be delivered
and processed without dropping any frame", then the AI processing rate must always
be at least the camera frame rate and the network must have sufficient capacity.
A real-time AI system should normally prioritize LOW LATENCY over processing stale
frames.

The reference implementation below therefore uses:
- C270 MJPEG capture on Pi
- one-frame-at-a-time transmission
- no unbounded frame queue
- direct TCP connection to laptop
- length-prefixed JPEG frames
- immediate decode on laptop
- newest-frame processing
- automatic reconnect
- no human prompts during normal operation

CRITICAL FIX DISCOVERED DURING TESTING
======================================
The C270 exposed this control:

    exposure_dynamic_framerate

Default observed value:
    1

Setting it to:
    0

removed the large frame-rate reduction observed during direct V4L2 streaming.

Observed before fix:
- approximately 14-15 FPS at 640x480 MJPG despite requesting 30 FPS
- direct v4l2-ctl tests also showed approximately 14-15 FPS

Observed after fix:
- approximately 28-30 FPS at 640x480 MJPG
- approximately 28-30 FPS at 1280x720 MJPG
- OpenCV achieved 596 good frames in approximately 20 seconds
- measured OpenCV capture rate was approximately 29.78 FPS

INITIAL BLACK FRAME BEHAVIOR
============================
The C270 can produce several dark/invalid initial frames after opening.

Observed examples:
- individual tests sometimes became clear around the third frame
- one 1280x720 MJPG diagnostic showed frames 1-22 with mean brightness 2.00
- frame 23 became valid with mean brightness 37.82
- subsequent frames remained around 37.x

Therefore:
DO NOT use a hard-coded "sleep 1 second and capture one frame" as the
production warm-up strategy.

Instead:
1. Open the camera.
2. Continuously read frames.
3. Validate each frame.
4. Discard only invalid initial frames.
5. Begin AI processing as soon as a valid frame arrives.
6. Do not accumulate discarded frames.

This is a warm-up/validation stage, not a frame buffer.

PI LIVE CAMERA SENDER
=====================
Create this file on the Raspberry Pi:

    nano ~/presento_camera_sender.py

Production code:

    import cv2
    import socket
    import struct
    import time
    import os
    import sys

    LAPTOP_IP = os.environ.get("PRESENTO_LAPTOP_IP", "10.241.151.100")
    LAPTOP_PORT = int(os.environ.get("PRESENTO_CAMERA_PORT", "5001"))

    CAMERA = "/dev/video0"
    WIDTH = 1280
    HEIGHT = 720
    FPS = 30
    JPEG_QUALITY = 85

    RECONNECT_DELAY = 2.0
    CAMERA_REOPEN_DELAY = 1.0

    def configure_camera():
        cap = cv2.VideoCapture(CAMERA, cv2.CAP_V4L2)

        if not cap.isOpened():
            return None

        cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*"MJPG"))
        cap.set(cv2.CAP_PROP_FRAME_WIDTH, WIDTH)
        cap.set(cv2.CAP_PROP_FRAME_HEIGHT, HEIGHT)
        cap.set(cv2.CAP_PROP_FPS, FPS)

        actual_width = int(cap.get(cv2.CAP_PROP_FRAME_WIDTH))
        actual_height = int(cap.get(cv2.CAP_PROP_FRAME_HEIGHT))
        actual_fps = cap.get(cv2.CAP_PROP_FPS)

        print(
            f"Camera opened: {actual_width}x{actual_height} "
            f"@ {actual_fps:.2f} FPS",
            flush=True
        )

        return cap

    def valid_frame(frame):
        if frame is None:
            return False

        if frame.size == 0:
            return False

        h, w = frame.shape[:2]

        if w < 320 or h < 240:
            return False

        # Detect the known black/invalid startup condition without
        # introducing a fixed warm-up delay.
        mean_value = float(frame.mean())
        min_value = int(frame.min())
        max_value = int(frame.max())

        if mean_value <= 2.5 and min_value >= 1 and max_value <= 3:
            return False

        return True

    def connect_laptop():
        while True:
            try:
                sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
                sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
                sock.connect((LAPTOP_IP, LAPTOP_PORT))
                print(
                    f"Connected to Presento laptop at "
                    f"{LAPTOP_IP}:{LAPTOP_PORT}",
                    flush=True
                )
                return sock
            except OSError as exc:
                print(
                    f"Connection failed: {exc}; retrying...",
                    flush=True
                )
                time.sleep(RECONNECT_DELAY)

    def send_frame(sock, encoded):
        payload = encoded.tobytes()
        header = struct.pack("!I", len(payload))
        sock.sendall(header)
        sock.sendall(payload)

    def main():
        # The v4l2-ctl command is normally applied by the startup service.
        # This process also configures OpenCV explicitly.
        while True:
            cap = configure_camera()

            if cap is None:
                print("Camera unavailable; retrying...", flush=True)
                time.sleep(CAMERA_REOPEN_DELAY)
                continue

            sock = connect_laptop()

            try:
                while True:
                    ret, frame = cap.read()

                    if not ret or frame is None:
                        print("Camera read failed; reopening...", flush=True)
                        break

                    if not valid_frame(frame):
                        # Drop only the invalid startup frame.
                        # Do not enqueue it.
                        continue

                    ok, encoded = cv2.imencode(
                        ".jpg",
                        frame,
                        [cv2.IMWRITE_JPEG_QUALITY, JPEG_QUALITY]
                    )

                    if not ok:
                        continue

                    try:
                        send_frame(sock, encoded)
                    except OSError as exc:
                        print(
                            f"Laptop connection lost: {exc}",
                            flush=True
                        )
                        break

            finally:
                try:
                    sock.close()
                except Exception:
                    pass

                cap.release()

            time.sleep(RECONNECT_DELAY)

    if __name__ == "__main__":
        try:
            main()
        except KeyboardInterrupt:
            print("Camera sender stopped.", flush=True)
            sys.exit(0)

WHY THE SENDER HAS NO FRAME QUEUE
=================================
The sender performs:

    capture
      ->
    validate
      ->
    JPEG encode
      ->
    send

There is no:
- Python Queue
- list of pending frames
- disk cache
- video file
- batch
- multi-frame backlog

The socket may still contain operating-system network data because TCP requires
kernel socket buffers. That cannot be eliminated by Python.

For true lowest-latency behavior, TCP_NODELAY is enabled.

LAPTOP LIVE RECEIVER
====================
The laptop receiver accepts the Pi connection and reconstructs each JPEG frame.

Create:

    presento_camera_receiver.py

Code:

    import cv2
    import socket
    import struct
    import numpy as np
    import threading
    import time

    HOST = "0.0.0.0"
    PORT = 5001

    latest_frame = None
    frame_lock = threading.Lock()
    running = True

    def recv_exact(sock, size):
        data = bytearray()

        while len(data) < size:
            chunk = sock.recv(size - len(data))

            if not chunk:
                return None

            data.extend(chunk)

        return bytes(data)

    def client_worker(conn, address):
        global latest_frame

        print(f"Pi connected: {address}", flush=True)

        conn.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

        try:
            while running:
                header = recv_exact(conn, 4)

                if header is None:
                    break

                frame_size = struct.unpack("!I", header)[0]

                # Prevent corrupted network data from allocating arbitrary
                # memory.
                if frame_size <= 0 or frame_size > 5_000_000:
                    print(
                        f"Invalid frame size: {frame_size}",
                        flush=True
                    )
                    break

                jpeg = recv_exact(conn, frame_size)

                if jpeg is None:
                    break

                array = np.frombuffer(jpeg, dtype=np.uint8)
                frame = cv2.imdecode(array, cv2.IMREAD_COLOR)

                if frame is None:
                    continue

                # Only one latest frame is retained.
                # An older frame is overwritten immediately.
                with frame_lock:
                    latest_frame = frame

        except OSError as exc:
            print(f"Receiver socket error: {exc}", flush=True)

        finally:
            conn.close()
            print(f"Pi disconnected: {address}", flush=True)

    def server_loop():
        server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        server.bind((HOST, PORT))
        server.listen(1)

        print(f"Presento camera receiver listening on {HOST}:{PORT}")

        while running:
            conn, address = server.accept()

            worker = threading.Thread(
                target=client_worker,
                args=(conn, address),
                daemon=True
            )

            worker.start()

    def get_latest_frame():
        with frame_lock:
            if latest_frame is None:
                return None
            return latest_frame.copy()

    def main():
        server_thread = threading.Thread(
            target=server_loop,
            daemon=True
        )
        server_thread.start()

        print("Presento camera receiver started.")

        while True:
            frame = get_latest_frame()

            if frame is None:
                time.sleep(0.005)
                continue

            # This is the integration point for Presento AI.
            # Replace this section with:
            #
            # result = presento_vision.process(frame)
            #
            # Do not add an unbounded frame queue here.
            #
            # Example:
            #
            # result = process_presento_frame(frame)
            # handle_attendance_result(result)

            cv2.imshow("Presento Live Camera", frame)

            key = cv2.waitKey(1) & 0xFF

            if key == 27:
                break

        cv2.destroyAllWindows()

    if __name__ == "__main__":
        main()

LATEST-FRAME SEMANTICS
======================
The receiver deliberately stores only:

    latest_frame

It does not store:
    frame1
    frame2
    frame3
    frame4
    ...

This prevents latency from increasing when the AI takes longer than the camera.

If Presento AI processing is fast enough to process every frame, frames will be
processed continuously. If AI processing is slower, stale frames are replaced.

For attendance recognition, this is normally more useful than building a queue
that causes the AI to recognize a face from several seconds ago.

LOW-LATENCY RULES
=================
Rule 1:
Never create an unbounded frame queue.

Rule 2:
Never save frames to disk during normal operation.

Rule 3:
Never wait for a human to approve a frame.

Rule 4:
Do not intentionally sleep between frames.

Rule 5:
Use TCP_NODELAY for the low-latency TCP connection.

Rule 6:
Decode each received JPEG immediately.

Rule 7:
Keep only the newest decoded frame for the AI worker.

Rule 8:
If AI processing is slower than capture, overwrite stale frames instead of
building latency.

Rule 9:
Do not use MP4 encoding in the production camera path.

Rule 10:
Automatically reconnect after network failure.

Rule 11:
Automatically reopen the camera after capture failure.

Rule 12:
Automatically reapply the known V4L2 camera configuration when the camera
process starts.

FRAME VALIDATION
================
The C270 demonstrated startup frames where:

    mean = 2
    min = 2
    max = 2

A basic invalid-frame test can therefore reject this known state.

Production validation should additionally check:
- frame is not None
- correct dimensions
- non-zero image size
- reasonable luminance
- optional blur metric
- optional face presence

Do not reject frames merely because no face is visible. A camera frame can be
valid even when nobody is in front of the camera.

NETWORK FAILURE RECOVERY
========================
If the Pi cannot connect:

    retry every 2 seconds

If the connection is lost:

    close socket
    reconnect
    continue capture

The sender should not terminate permanently because the laptop was temporarily
offline.

CAMERA FAILURE RECOVERY
=======================
If cap.read() fails:

    release camera
    wait approximately 1 second
    reopen camera
    reapply camera configuration
    reconnect if necessary
    continue

Do not ask the user for confirmation.

CAMERA INITIALIZATION SCRIPT
============================
For deterministic startup, create:

    ~/presento_camera_init.sh

Code:

    #!/bin/bash
    set -e

    DEVICE="/dev/video0"

    /usr/bin/v4l2-ctl -d "$DEVICE" --set-ctrl=exposure_dynamic_framerate=0

    /usr/bin/v4l2-ctl -d "$DEVICE" \
        --set-fmt-video=width=1280,height=720,pixelformat=MJPG \
        --set-parm=30

    echo "Presento C270 initialized"

    /usr/bin/v4l2-ctl -d "$DEVICE" --get-fmt-video
    /usr/bin/v4l2-ctl -d "$DEVICE" --get-parm

Make executable:

    chmod +x ~/presento_camera_init.sh

Run:

    ~/presento_camera_init.sh

If using systemd, the ExecStartPre commands are sufficient and the separate
script is optional.

KNOWN WRONG APPROACHES
======================
1. Using rpicam/libcamera for the C270 USB webcam
-------------------------------------------------
The Pi previously reported:

    rpicam-hello: No cameras available!

That does not mean the USB C270 is broken. The C270 is a UVC USB webcam and
should be handled through V4L2/uvcvideo.

2. Assuming a one-second sleep fixes startup black frames
---------------------------------------------------------
It did not reliably fix the problem.

Use frame validation instead.

3. Assuming OpenCV is the only reason for low FPS
--------------------------------------------------
Direct v4l2-ctl streaming also measured approximately 14-15 FPS before the
exposure_dynamic_framerate fix.

4. Using YUYV at 1280x720
-------------------------
The tested camera negotiated approximately 10 FPS at this resolution.

Use MJPG.

5. Writing video to disk for live AI
------------------------------------
This adds latency and is not the production architecture.

6. Creating an unbounded queue
------------------------------
This causes latency to grow when AI processing falls behind.

Use latest-frame semantics.

7. Guessing V4L2 control names
--------------------------------
Use:

    v4l2-ctl -d /dev/video0 --list-ctrls

and use the exact controls exposed by the device.

PROTOCOL RECOMMENDATION
=======================
Current simple protocol:

    [4-byte unsigned big-endian JPEG length]
    [JPEG bytes]
    [4-byte unsigned big-endian JPEG length]
    [JPEG bytes]
    ...

Advantages:
- simple
- no text prompts
- no file system dependency
- frame boundaries are explicit
- OpenCV decodes directly
- easy to implement on Pi and Windows
- no unbounded application queue

Potential future protocol header:

    magic
    version
    camera_id
    sequence
    timestamp
    jpeg_length
    jpeg_payload

This should be added only if Presento needs multi-camera synchronization,
diagnostics, or stronger metadata.

PERFORMANCE EXPECTATIONS
=========================
Target:
    1280x720
    MJPG
    30 FPS

The C270/Pi test achieved approximately 29.78 FPS through OpenCV after the
exposure_dynamic_framerate fix.

End-to-end AI FPS may be lower because face detection, liveness, recognition,
network transfer, JPEG decoding, and database operations consume CPU time.

The camera capture rate and AI processing rate are separate metrics.

Do not change the camera to a lower FPS merely to make the AI appear faster.
First measure:
- capture FPS
- network receive FPS
- decode FPS
- AI processing FPS
- recognition FPS

If recognition is expensive, process the newest available frame rather than
processing stale frames.

ATTENDANCE EVENT TIMING
=======================
A recognition result should include an event timestamp generated close to the
actual frame processing/capture time.

Do not use the time a queued frame happens to be processed if the frame is old.

If timestamps are added to the transport protocol, use the Pi capture timestamp
for camera-time measurements and laptop receive time for network diagnostics.
